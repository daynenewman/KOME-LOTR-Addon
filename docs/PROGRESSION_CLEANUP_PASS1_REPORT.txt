D. RECRUITMENT AUTHORITY
=========================

Ordinary hire:
KOMEEvents.handleHiredUnit no longer checks HIRE_UNITS. It still observes native
ownership/task, avoids secondary mount/double registration, requires the established
combat population pledge, calculates the same unit cost and uses
KOMENativeHireRegistrationService.registerOrdinaryCombatHire.
The stored class stays ORDINARY; no company admission or strategic mobilization occurs.
Native trading/hiring checks and coin deduction still precede this observation hook.

The ordinary foreign-warrior branch previously demanded retired political
stewardship. Ordinary bodyguards are now outside that Campaign authority rule and
spend their recruiter's bank, preserving the NPC's native faction and ordinary
classification. This follows the accepted native-follower/KOM-76 distinction;
it does not authorize foreign Campaign recruitment or foreign army control.

Farmhands:
Military progression flags are not checked. Native price, AI/task and existing
classification remain. KOME cost/populationSpent remain zero, no company enrollment.
The existing foreign Stage 1 Cooperation check remains specifically for farmhands;
this pass does not guess a new Friends/Allies agricultural policy.

Campaign hire:
KOMEProgressionPermissions.campaignRecruitmentDenial is a narrow current-operation
check, not the future rank-ability framework. For a normal new Campaign hire:
1. Current canonical rank must be Lord or Prince (not historical Knight/title flags).
2. Current observed pledged population faction must match the spending faction.
3. Actor must currently hold that faction's recognized ruler office.
   Non-ruler Lords receive the explicit KOM-87 delegation-not-implemented blocker.
4. Existing governance, native trade/coins, legal selected/default recruitment tile,
   physical deployment, faction bank debit, Campaign classification/admission and
   transaction rollback all remain authoritative.

The real native adapter derives administrative permission on the SERVER from
canCommandSenderUseCommand(2,"troops"). It is stored only in trusted PreparedRecruitment,
not Request or the client packet. Explicit server admin authority bypasses the new
rank/office floor, not native price, location, bank, unit/class or governance checks.
The adapter checks authority before creating a new NPC candidate; the common
transaction rechecks it before deployment or economic/native effects, including
future source adapters. Request fields remain trader ID, trade index and squadron;
there is no client-supplied rank, administrative bit, price, population or territory.

The political ruler is an existing explicit Crown authority under KOM-87's design
(the ruler needs no own credential). A Lord title alone, a company delegation,
legacy HIRE_UNITS flag, disabled progression or arbitrary credential item is not
a grant. No persisted recruitment warrant provider exists here, so no officer is
silently treated as having unlimited delegated bank access.

Population:
Canonical costs, mounted surcharge, overrides, centi-population accounting,
permanent/high-water investment, legal recruitment-location rules and farmhand
zero-cost treatment are unchanged. Both ordinary and Campaign combat hires spend
the same established bank. Existing duplicate detection/record admission/debit
rollback remains; native re-observation of an already tracked hire does not pay twice.

Existing units:
No recruitment-floor check was added to existing troop ownership, company control,
movement, retreat, recovery, conflict egress or terminal cleanup. No army removal,
classification conversion, refund or retroactive charge. Existing pledge-release
semantics and conflict-protected recovery are unchanged. Separate explicit ordinary
mobilization has no production workflow in this checkout; it was not reimplemented.
Any future mobilization must consume its own legal authority/identity/location/reset
transaction without charging the prior purchase again.

Kingless:
Current supportingKingDecision denies retired KOM-31 stewardship. That is not revived
as a substitute Crown budget. The real KOM-75 Emergency Defense mobilization path
uses separate reserves/conflicts/native-force ownership and is untouched.

Remaining dependency: KOM-87 canonical grants, scope/budget/revocation/commit semantics.
The proposed Lord 200-population ceiling is not implemented or emulated with the
faction payout cap. Its exact accounting/legacy policy still needs a decision.

E. CONQUEST AUTHORITY
======================

Unsafe prior path:
KOMEPacketConquestClaim required pledge plus TAKE/RECLAIM flag/current Lord, then
KOMEConquestClaimService.claim called claimTile and recordHostileCapture. The latter
could create a war and apply Mortal Enemy diplomacy; a fingerprinted second click
was not political authority or actual battle evidence.

Safeguard:
The existing player claim service now returns a read-only denial. It validates the
known target/pledge or explains already-owned status, but never calls claimTile,
recordHostileCapture, changes confirmation state, advances timers or grants victory.
Rank/achievement checks no longer masquerade as sufficient claim authority.
Forged/replayed packets reach the same service and are denied even with progression
disabled. Existing historical confirmations remain loadable but confer no authority.

Tile Command canClaim is generated from the same denial policy. The compact disabled
Conquest button explains battle resolution or existing ownership, not a missing
"Take Waypoints" advancement. Old claim-confirmation/war-destination presentation
is not armed. No separate victory interface or progression-owned battle resolver.

Preserved legitimate paths:
- KOMEPacketConquestTransfer sovereign offer/accept/cancel, existing player ruler
  authorization, native valid target factions and both-ruler requirements.
- KOMECommandConquest explicit staff correction/transfer operations.
- KOMEWorldData.claimTile as the existing authoritative mutation seam for validated
  domain/staff operations; WarService/DiplomacyService remain their existing owners.
- Existing ConflictService commitments, Join Battle, formal retreat/abandonment,
  defense and territorial state persistence.

Allies, friends, neutral, enemies, mortal enemies, already-owned and unclaimed cases
are covered by the denial tests. Genuine peaceful ruler transfer still succeeds;
the safeguard is not a ban on all peaceful/allied operations. Staff transfer remains
functional. A ruler office also does not manufacture battle evidence for manual claim.

Integration limit:
The later KOM-18 resolver, configurable response timers, winner/continuity selection,
fortified completion, recovery WAL and authoritative outcome commit are not in the
local baseline. This pass preserves the existing conflict code rather than copying
or recreating those systems. Full concluded-battle-to-capture/reclaim acceptance is
BLOCKED on deliberate integration of that contributor work. A legal political
occupation of unclaimed land is not silently invented; its manual intent fails safely.

F. CLIENT/SERVER CONSISTENCY
=============================

Before: ProgressionData updated static book/title summaries but not
KOMEClientData.progressions, which legacy permission/waypoint readers use.

After:
- Server packet carries authoritative UUID, stable canonical rank key, progression
  enabled mode, dimension and monotonic publication revision plus existing completion,
  assignment, cultural rank/service and relationship presentation.
- Packet counts/text are bounded; unknown machine rank and mismatched g8 header fail.
- Real client proxy copies mutable collections, queues on the existing client task
  queue, verifies current connection/world epoch and viewer/dimension, then accepts
  only newer revisions. No rank is inferred from cultural display-title text.
- KOMEClientData accepts one transient viewer projection, replacing rank/completion/
  faction/mode coherently BEFORE book/title publication. Both current consumers read
  that accepted state; all server actions still validate their own authority.
- Connect/disconnect reset clears state and queued work. Dimension unload clears
  visible values, retains the connection revision fence, invalidates pending intake
  and requests fresh state once a usable client world/connection exists.
- Login already syncs explicitly; respawn/dimension now sync progression too. Native
  pledge changes sync on observation. Rank/admin/advancement paths retain existing
  immediate publication. Periodic diff publication catches permission-affecting rank,
  native pledge/alignment, enabled mode and assignments even when no flag was granted.
- Server publication/signature memory is transient, cleared for session/logout;
  no new NBT, unlock ledger or client authority was introduced.

Waypoints use the accepted faction on client policy evaluation once a server
projection exists, avoiding a conflicting older native pledge cache. Native region,
cooldown/under-attack/sleep/config and server request/final destination checks remain.
This does not implement Serf original-start return or a new waypoint ladder.

Protocol: 1.0.9-integration-g8. Packet IDs are unchanged, including Join Battle53-58,
progression identity59, progression data9 and marker43. Both ends require g8;
g7 interoperability is intentionally rejected, not claimed. Normal metadata/build
version was advanced without changing dependencies or persistent schemas.

Actual proxy tests execute queue/reset/accept/book/cache code using inert Minecraft
objects; stale revision, old connection, queued pre-unload and wrong-dimension
packets cannot overwrite accepted state. These are headless tests, not live network
or graphical acceptance.
