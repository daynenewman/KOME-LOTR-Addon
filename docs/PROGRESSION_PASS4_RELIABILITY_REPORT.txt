EXACT IMPLEMENTATION - THREE PRODUCTION FILES
1. src/main/java/kome/common/data/KOMEProgressionServiceLocation.java
   - Retains existing KOMERegionalSeat version 1, host/faction rules and native home check.
   - Generation requires the exact allowlisted native structure package/class name and
     entity/world agreement, rather than trusting a simple class name from another package.
   - Proof validation rejects malformed UUIDs and non-finite native home ranges.
   - captureReplacement records optional version-1 KOMERegionalSeatReplacement in the
     actual native LOTREntityTraderRespawn entity's ForgeData. Source must already pass
     regional proof/home validation, be the same-world adult unhired non-encounter combat
     trader, and have the native shouldTraderRespawn flag. Stale receipt capture is cleared.
   - Receipt binds carrier UUID, predecessor UUID/class, original proof and exact native
     home coordinates/range. It copies only provenance; no entity/NPC is manufactured.
   - replacementSpawned preserves the native boolean. Only successful native spawn with
     matching carrier, new identity, class, faction, dimension, home and eligibility can
     receive a copied proof rebound to the new UUID. Final regional validation must pass.
     It consumes the receipt once on verified success. A failed native spawn keeps it for
     native retry; malformed/mismatched data publishes no seat proof. Existing target proof
     is not overwritten. Copied generic receipts on a different carrier fail identity checks.
   - It never copies player relationship leases, explicit elevated NPC ranks, Crown office,
     recommendations, service credits, NPC inventory or military rights to the replacement.
     Ordinary native death/relationship/history behavior remains authoritative.
2. src/main/java/kome/core/KOMEProgressionSeatTransformer.java
   - Uses its EXISTING coremod registration, retaining all generation hooks.
   - Observes the native item-package LOTREntityTraderRespawn.copyTraderDataFrom return.
   - Wraps that class's native World spawn call after native initialization/home restoration;
     forwards its original success boolean through replacementSpawned unchanged.
   - Idempotent transform; no extra transformer, event-based guess, NPC factory or packet.
3. src/main/java/kome/common/data/KOMESerfdomMasterService.java
   - Keeps authoritative current Master/rank/pledge/range/betrayal/active-work validation.
   - Builds the same eligibility-filtered candidate pool and shuffles ONCE with world RNG.
     Walks each candidate at most once; completed duties and equivalent delivery exclusions
     remain. A success immediately ends selection; no accepted assignment is rerolled.
   - Objective preparation uses a detached Serf/Knight state copy. Failed escort destination
     preparation cannot leak trial/variety changes or bind a charge. Actors/encounters are
     activated only after one assignment is accepted into canonical state.
   - Delivery preparation checks eligible goods/material pools and validates complete NBT
     before acceptance. Missing legitimate goods may fall through without a partial task.
   - Courier route/correspondent failure continues to another type. A native rejected dispatch
     spawn restores the complete prior duty/relationship/reward/variety state before fallback.
     Already-reported credits and historical recommendation records remain untouched.
   - Uses existing assignment/issuance/objective services, not another quest framework.
     An authority/state denial is not treated as a retryable preparation failure. Unexpected
     exceptions are not swallowed as ordinary infeasibility. Once accepted, technical encounter
     activation uses its existing saved retry/reassignment path instead of issuing other work.
   - If all preparations fail, returns bounded type-specific reasons and confirms service is
     preserved; it does not invent a settlement, charge, correspondent, property or reward.

LEGACY ADOPTION - DEFERRED, WITH REASON
LOTRVillagePositionCache is a bounded in-memory HashMap (20,000 entries, clearCache), not a
persisted ledger of built structure types, successful NPC spawns or UUIDs. LocationInfo records
coordinates/rotation/name and fixed-waypoint context, including RANDOM_GEN_HERE and
SPAWNED_BY_PLAYER sentinels; none binds a native noble to a completed regional structure.
LOTRVillageGen recomputes/sets up AbstractInstance structure lists using world seed/location.
Its StructureInfo describes planned generators and coordinates, without a saved successful
spawn receipt. Decorator-built towers/camps do not acquire a universal persisted component
registry through these classes. A possible predicted building is not an actual structure
receipt. NPC home/location text also lacks the generating class and original spawn identity.

Consequently no trustworthy general automatic adoption rule was found. The implementation
continues rejecting untagged old homes/nobles, wandering nobles, copied UUID proofs, malformed
receipt fields, wrong factions/dimensions/classes, changed homes and unproven respawners.
Existing accepted relationships remain valid without retroactive seat proof requirements;
existing death/faction-change cleanup still applies normally. A carrier already queued before
Pass 4 cannot recover its lost predecessor proof and remains an explicit compatibility limit.
These are server-owned provenance records, not cryptographic authentication against an
administrator who can rewrite arbitrary trusted server NBT.

Separately reviewable remedy proposal (NOT IMPLEMENTED): an operator-only, dry-run-first,
single-NPC adoption tool with explicit stopped-world evidence review, exact world/NPC UUID,
native class/faction/home, verified actual structure evidence, bounded scope and durable audit.
A human would approve evidence for each adoption; a seed prediction or block/roof/waypoint
radius alone would not authorize it. It must never spawn/replace an NPC or transfer a player's
relationship. Its policy, evidence requirements and tests require separate review.
