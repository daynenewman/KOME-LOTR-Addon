## Checkpoints

1. KOM-65/68: immutable approved records and proposal/review history in an additive versioned PublicWaypoints sub-section of KOMEWorldData root schema 5. Absence means an empty new registry, not migration of strategic rally/entry points or legacy native links. Stable UUID plus persisted reserved wire ID; zero-or-one approved record per tile, strict names/positions/source/level validation. Native associations are explicit, exact-position validated administrative actions, not automatic guesses about known waypoint aliases. Level is nonnegative int metadata only; owners are derived on every canonical API read from tile state. Loader quarantines malformed/orphaned/conflicting rows with original evidence; no order-dependent duplicate winner. Unavailable geometry suspends visibility/travel instead of deleting persisted records. Wrong section/schema types reject the candidate atomically.
2. KOM-66: one complete bounded public snapshot (only approved currently valid records plus migration aliases and server-derived owners) automatically sent on login, changes and retry after failure; queued client application uses existing session fencing and clears on connect/disconnect/server switch. Keep packet IDs append-only. No native custom/fellowship list mutation or saving. LOTRPlayerData.getAllAvailableWaypoints returns a newly composed presentation list through a narrow addon ASM hook; native entries are retained except exact native associations or explicitly migrated legacy identities represented by an approved public marker. Public markers subclass LOTRCustomWaypoint so v36.15 map casts, rendering, safe-Y resolution and cooldown/use-count paths remain valid. They use reserved negative IDs and an addon UUID namespace, never personal/fellowship waypoint IDs.
3. Preserve the existing normal LOTR travel request and final guard. A narrow early hook in the already-transformed LOTRPacketFastTravel.Handler recognizes only the public namespace and schedules validated travel via the established KOME server-thread queue. All other packets continue unmodified. Resolve current canonical approval, coordinates/tile, source/native progression, global travel config, progression permission, KOM-14 diplomacy/current owner, cooldown/combat/sleep/configured dimension before setTargetFTWaypoint. Final guard rechecks approval, current destination/position and policy after delay. Do not bypass cooldown or invent level gates. Native-associated markers retain native region progression. Public markers use existing custom-waypoint eligibility semantics. Canonical objects stay immutable despite native map rename/hide controls; native mutations cannot alter registry. Inspect those control paths and prevent misleading local edit/hide affordances for public markers.
4. KOM-67: /kome waypoint propose uses server player position for any normal player; pending records are never synchronized/travelable. Bound pending proposals explicitly, at most one per submitter/tile and a documented per-tile resource cap; allow competing submitters with visible rejection diagnostics. Level-two administrative pending/inspect/adjust/approve/reject/rename/move/remove/level/associate commands check permission before WorldData access. Revalidation and approval are one server operation; preserve submitting/review identities, times, reasons and edits through restart. Moves recheck destination uniqueness and exact tile membership.
5. KOM-69: explicit selected-fellowship read-only inventory dry run, bounded and fingerprinted, using original owner/custom IDs, names and coordinates. Diagnose invalid/unknown gaps, wrong dimension/height, duplicate identities, same-tile conflicts and existing-approved conflicts without nearest-tile inference. Explicit conversion selection re-inventories/revalidates to reject stale dry runs, commits canonical records and persistent cutover identities together. Presentation filters only exact converted legacy identities, including later joins/reconnect/restart; originals and shared fellowships are untouched. Provide explicit rollback of cutover aliases. Test with disposable fixture inventory and composed native lists. Existing real inventory is not accessed here and remains a rollout blocker until authorized inventory is supplied/run.
6. Meaningful persistence/atomic rejection/quarantine/competing approvals/ownership/level, wire decode and session/retry lifecycle, native hook bytecode and travel-policy tests; compile and clean test/build, addon packaging and Java 8 checks. Available disposable-server startup/save/restart checks on new isolated fixtures, no existing runtime refresh. Full self-review, read-only Claude diff review, verified corrections and reruns; commit checkpoints, scoped Linear evidence, push and PR dev, no merge/deploy.
